Scheduling ds_load on GFX1250 with a DAG mutation

Target: AMD GFX1250 / MI450, CoExecScheduler (pre-RA) · status: PRs open · public PR · artifact

TL;DR

The pre-RA scheduler, run on MI450, tends to bunch many ds_loads (LDS load instructions) at the head of a GEMM inner loop. Looking into the CoExecScheduler, it turned out that because the scheduler greedily schedules an instruction whenever one is available, there are moments where the only instructions available — and therefore the ones scheduled — are ds_loads for data consumed much, much later.

That does two bad things at once:

  • it forces the WMMAs to sit behind long s_wait_dscnt stalls;
  • it inflates register pressure, because the live ranges are needlessly long.

The DAG mutation in AMDGPUWMMASchedule.cpp adds hard constraints on where these loads may sit relative to the WMMAs that consume them. That spreads the loads out and stops the scheduler from greedily issuing them far too early. The mutation is also (statically, and rather naively) aware of register pressure, so those constraints form a window in which each load can be scheduled without causing excessive spills.

Why do we want the DAG mutation?

To understand why the mutation is necessary we should first look at the pre-RA scheduler — its strengths, and more importantly its weaknesses.

The CoExecScheduler

The mutation is largely independent of any particular scheduler, but there is an intention to move the AMDGPU backend to the CoExecScheduler in future, so everything below is measured against it. CoExec is a pre-RA machine scheduler strategy for GFX1250; it replaces the generic bottom-up/top-down instruction scheduler run before register allocation. It is selected when amdgpu-sched-strategy == "coexec", is gated to gfx1250 only, and is assembled in AMDGPUCoExecSchedStrategy.cpp as a GCNScheduleDAGMILive driven by AMDGPUCoExecSchedStrategy plus two DAG mutations (three, counting ours).

Co-execution windows

The whole point of CoExec is that multi-cycle instructions (WMMAs, TRANS, multi-cycle VALU) can be scheduled alongside other instructions that run in parallel. Each multi-cycle op exposes a window of slots, and each slot has rules about which instruction types may legally co-execute there (a correctness constraint, which cannot be violated) and which are preferred there (a performance one, which can).

How each ready instruction is chosen

Everything goes through AMDGPUCoExecSchedStrategy::tryCandidateCoexec. Given two candidates it applies tie-breakers in a fixed priority order, and it is a cascade: it returns at the first rung that discriminates, so the rungs below never run.

The widget below mirrors pickNodeFromQueue. One pass is made over the whole queue; each instruction in turn becomes the candidate and is compared against the reigning winner, and the loser is discarded. Nothing is issued mid-scan — only when the pass ends does pickNode schedule whichever winner survived. Click any heuristic to read what it does.

The issue with this scheduler

This scheduler is greedy, like other schedulers. Whenever an instruction is available to be scheduled, an instruction will be scheduled. The problem is that there are moments when the only available instructions are ds_loads that will not be consumed for a long time. No amount of tie-breaking can prevent that, because CoExec has no way to reject every available instruction and schedule nothing instead. So the loads go out far too early, simply because the scheduler ran out of anything else that could win.

That is the gap the DAG mutation fills — not by adding another heuristic, but by removing those loads from the queue until the point where issuing them is actually reasonable.
